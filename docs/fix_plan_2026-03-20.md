# Fix Plan — Same-Line Speed, Doom Loading, Config Persistence

## Problem 1: Same-Line Cache Suppress-Skip Crashes CPU

### Symptom
When `cache_hit_d1` stays asserted for consecutive cycles (same-line optimization),
the CPU executes garbage and enters 65C816 native mode unexpectedly. UART shows
C:0000 (zero cache hits), random addresses, and opcodes $07/$00 (ORA dp indirect
long / BRK).

### Root Cause Analysis

The crash happens because **`cache_di` is combinational but depends on `line_word`
which is registered**. The timing chain:

1. Edge N: `cache_hit_d1='1'`, CPU reads `cpuDi = cache_di`. CPU advances.
   M10K reads `line_word <= data_banks(line_index)` — using the OLD address.
   `prev_line <= line_index` (OLD address).

2. Edge N+1: CPU has NEW address. `line_index` = new addr's line.
   `same_line = (line_index == prev_line)` — comparing NEW with OLD.
   If same line: `cache_hit_d1 <= '1'` (skip suppress).
   `cache_di = byte_select(line_word, byte_offset)` — BUT `line_word` was
   read at edge N with the OLD line_index!

**If same line, this IS correct** — same line = same M10K word.

So the data path SHOULD be correct for same-line accesses. The crash must come
from something else. Possible causes:

**Theory A: The CPU needs the suppress cycle for internal state update.**
The P65C816 might need a cycle between enable pulses to complete its internal
state machine. Some 65816 bus cycles are "internal operations" (VDA=VPA=0)
where the CPU doesn't read external data. If we keep `cache_hit_d1` asserted
during these cycles, the CPU gets spurious enables.

The `bram_valid_cycle` guard (`vda_816 or vpa_816`) should catch this. But
`bram_valid_cycle` is evaluated AT the same edge as `cache_hit_d1`. If the CPU
outputs VDA/VPA on the same edge as the new address, then `bram_valid_cycle`
reflects the NEW cycle's VDA/VPA. For internal cycles, VDA=VPA=0 and the guard
blocks. This SHOULD work.

BUT: there's a 1-cycle lag. VDA/VPA are CPU outputs, registered. At edge N,
the CPU processes the current bus cycle and updates VDA/VPA for the NEXT cycle.
So at edge N+1, VDA/VPA reflect what the CPU needs at N+1. If N+1 is an
internal cycle, VDA=VPA=0 at edge N+1. The `bram_valid_cycle` guard at N+1
would correctly block `cache_hit_d1`. So Theory A should be handled.

**Theory B: The suppress cycle provides time for cache fill to complete.**
After a cache miss, the SDRAM fills the cache line. If the suppress cycle
is skipped, a subsequent same-line access might read an incompletely-filled
line (some bytes valid, others not). The `byte_valid` check in `cache_hit`
should prevent this. Theory B is unlikely.

**Theory C: Race between cache_di and cpuDi mux selection.**
`cpuDi = cache_di when (cache_hit_d1 = '1')`. When `cache_hit_d1` stays '1'
for consecutive cycles, `cpuDi` is always `cache_di`. But `cache_di` changes
combinationally as `byte_offset` changes (new address from CPU). The CPU's
`di` port reads `cpuDi` on the rising edge. If `cache_di` is still settling
when the edge arrives (setup time violation), the CPU reads metastable data.

**Theory C is the most likely root cause.** The combinational path is:
`cpuAddr_816 (reg) → cpuAddr_pre (combo) → cpu_addr → byte_offset (combo)
→ line_word MUX (combo) → cache_di (combo) → cpuDi (combo) → CPU di port`

This is a long combinational chain that must settle within one 32MHz clock
period (31.25ns). If the chain is too slow, the CPU reads wrong data.

**The suppress cycle normally gives this chain an extra 31.25ns to settle.**

### Proposed Fix

**Option A: Register the byte-select MUX output.**
Add a pipeline register between `cache_di` and `cpuDi`:
```vhdl
-- In cpu_cache.vhd:
process(clk) begin
    if rising_edge(clk) then
        cache_di_reg <= byte_select(line_word, byte_offset);
    end if;
end process;
cache_di <= cache_di_reg;  -- 1-cycle delayed but always stable
```
This adds 1 cycle of latency to ALL cache reads, which is exactly the suppress
cycle. But for same-line accesses, the registered output is still 1 cycle behind.
This doesn't help.

**Option B: Dedicated same-line output with registered byte select.**
Add a second data output that uses the PREVIOUS cycle's line_word with the
CURRENT byte_offset, registered:
```vhdl
process(clk) begin
    if rising_edge(clk) then
        cache_di_fast <= byte_select(line_word, byte_offset);
    end if;
end process;
```
When same_line='1', use `cache_di_fast` (registered 1 cycle ago from the
same line_word). For different-line accesses, use the normal suppress path.

**This is equivalent to what we already have!** The suppress cycle IS this
registration. The suppress + re-evaluate pattern gives:
- Edge N: line_word read, byte_select computed
- Edge N+1: cache_di = byte_select (registered via suppress path)

So the suppress is fundamentally necessary for timing closure. **The only way
to eliminate it is to make the combinational path shorter** — fewer MUX stages,
or raise the clock frequency headroom.

**Option C: 2-cycle lookahead — predict the next address.**
Instead of reacting to the CPU's new address, predict it: PC+1 for instruction
fetch, same address for data read. Pre-compute the byte select for PC+1 and
have it ready when the CPU advances.

This requires knowing the CPU's fetch/execute state, which is complex. But for
sequential instruction fetches (the common case), PC+1 is trivially computable.

### Recommendation

**Option C (lookahead) is the most promising** but also the most complex. Start
with verifying Theory C by checking Quartus timing reports for the cache_di path.
If the path violates timing, the fix is either:
1. Pipeline the byte-select (accept 1-cycle latency, keep suppress)
2. Optimize the combinational path (fewer MUX stages)
3. Implement PC+1 lookahead for instruction fetch acceleration

## Problem 2: Doom REU Loading

### Symptom
doom.reu (16MB) must be loaded into REU SDRAM, but there's no way to both
load the .reu file AND keep SuperCPU enabled:
- MGL loading resets OSD status (SuperCPU disabled)
- `mbc load_rom` doesn't send with correct ioctl_index for .reu
- Direct `load_core` reads config but can't load .reu simultaneously

### Root Cause
MiSTer framework's MGL mechanism resets all status bits to defaults. The config
file is not read during MGL load. The hardcoded `supercpu_enable = 1'b1` helps
but MGL still seems to suppress UART output (possibly a framework interaction).

### Proposed Fix

**Option A: Fix mbc to support .reu ioctl_index.**
The mbc tool needs to send ioctl_index=0x81 for .reu files. Check the mbc
source code to see if this can be configured. If mbc sends with the correct
index, we can: load core (reads config) → mbc send .reu → manually run loader.

**Option B: Use the existing REU OSD loading mechanism.**
The user can manually: F12 → Load → select doom.reu. This works but can't be
automated. Document this as the current workflow.

**Option C: Pre-load REU data from a file at boot.**
Modify c64.sv to load an REU image from a fixed SDRAM location at boot.
The .reu file would be uploaded to /media/fat/ and loaded via the ioctl
mechanism with a startup MGL.

### Recommendation

**Option A** is the quickest path if mbc can be patched. Otherwise **Option B**
(manual OSD) works and should be documented clearly.

## Problem 3: Turbo Speed (Currently 5.66x, Target 20x)

### Current Bottlenecks

1. **1-cycle cache suppress** — halves potential cache throughput.
   With 16 CPU slots per rotation, max 8 cache hits (suppress eats the other 8).
   Fix: same-line skip (blocked by crash, see Problem 1).

2. **SDRAM pipeline** — 3 cycles (cpu_cyc → cpu_cyc_s(0) → cpu_cyc_s(1) →
   enableCpu) block cache_hit_d1 via guards. Even when cancelled by cache hits,
   the pipeline fires every rotation at CPUC.
   Fix: CPUC skip (attempted, made things worse for I/O-heavy code).

3. **VIC badline stealing** — during badlines, baLoc='0' blocks cache hits.
   This is correct behavior (VIC needs the bus) but limits peak throughput.

### Speed Budget (32 slots per rotation)

| Slots | Current Use | Potential |
|-------|------------|-----------|
| EXT (8) | Unused by CPU | Could give to CPU with no VIC impact |
| DMA (4) | REU DMA | Steal when DMA inactive |
| VIC (4) | VIC reads | Cannot touch |
| CPU (16) | 8 cache + 3 pipeline + 5 idle | Optimize pipeline |

### Proposed Improvements (in priority order)

**A. Fix same-line suppress-skip (2x improvement)**
See Problem 1. This is the single biggest improvement. Would increase from
8 to potentially 16 cache hits per rotation.

**B. Use EXT slots for cache hits (up to +8 hits per rotation)**
Currently cache_hit_d1 is blocked during EXT/DMA/VIC slots by the guard
`(sysCycle < CYCLE_CPU0)`. If we allow cache hits during EXT slots (which
are unused for CPU), we could get 8 more cache hits per rotation.
Risk: must ensure EXT slot cache hits don't interfere with VIC/DMA timing.

**C. SDRAM burst mode (faster cold-miss recovery)**
Change sdram.v BURST_LENGTH from single to burst-of-4. Fill 8 bytes per
SDRAM access instead of 1. Reduces cold-miss penalty by 8x. Medium complexity.

**D. Pipeline optimization (reduce CPUC blocking)**
Instead of blocking cache_hit_d1 when cpu_cyc_s is nonzero, allow cache hits
to cancel the pipeline mid-flight. This requires careful handling of stale
SDRAM data that arrives after the cache hit.

### Recommendation

**Priority: A → B → D → C.** Focus on same-line first (2x), then EXT slots
(+50%), then pipeline optimization (+20%), then burst mode (cold-miss only).

With A+B, theoretical max = 24 cache hits per rotation = ~24MHz effective.
With the suppress halving (no A), max = 12 hits (EXT+CPU) = ~12MHz.
